## 二、关键修复

### 2.1 可执行 jar 与依赖 jar 分离（`classifier=exec`）

**问题**：`erp-order-service` 同时是「可部署的服务」和「其它模块的依赖库」。repackage 后主 artifact 变成 fat jar，依赖方无法从 classpath 读取类。

**方案**：repackage 加 `classifier=exec`，产出两个 jar：

```
erp-order-service-1.0.0-SNAPSHOT.jar        46KB   普通 jar（classes 在根目录）→ 供依赖方编译
erp-order-service-1.0.0-SNAPSHOT-exec.jar   114MB   fat jar                 → 供 docker / start.sh 部署
```

**同步修改**：
- `start.sh` → `java -jar erp-order-service/target/erp-order-service-1.0.0-exec.jar`
- `docker/Dockerfile.order` → `COPY .../erp-order-service-*-exec.jar ./order-service.jar`

> ⚠️ 注意：不要给该 execution 设置 `<id>`，否则会与 root pom `pluginManagement` 中的默认 repackage 并存，导致不带 classifier 的 repackage 再次覆盖主 artifact。

### 2.2 架构污染清理：`erp-common` 移除 JPA

**问题**：`erp-common` 引入 `spring-boot-starter-data-jpa`，传递给**所有**下游模块，导致只使用 MyBatis-Plus 的模块也被激活 Hibernate 自动配置。

**排查**：
- `erp-common` 自身**没有任何** JPA 实体（唯一关联是 `MultiTenantRepository` 继承 `JpaRepository`）
- `MultiTenantRepository` / `TenantContextHolder` / `TenantFilter` 三个类**全项目无人使用**（`erp-tenant-service` 有自己独立的 `TenantFilter`）

**处理**：
- 从 `erp-common/pom.xml` 移除 `spring-boot-starter-data-jpa`
- 删除死代码包 `erp-common/src/main/java/com/crossborder/common/tenant/`（3 个类）
- 真正使用 JPA 的 `erp-tenant-service` / `erp-social-commerce-service` **已各自显式声明** `data-jpa` 依赖，不受影响

### 2.3 实体字段补齐

| 实体 | 补齐字段 | 用途 |
|------|----------|------|
| `CustomerTag` | `description` | 标签描述 |
| `CustomerGroup` | `memberCount` | 分组成员数（冗余统计） |
| `CustomerFollowRecord` | `followTime`、`followerName` | 本次跟进时间 / 跟进人展示名 |
| `ReplenishmentSuggestion` | `urgencyLevel` | 补货紧急度 |

`urgencyLevel` 并非空字段——`ReplenishmentSuggestionService.calculateUrgencyLevel()` 实现了真实计算：

```
缺口 >= 80%  → HIGH    （库存几乎耗尽，需立即补货）
缺口 >= 50%  → MEDIUM  （库存已明显低于安全线）
其余         → LOW     （库存尚可，按计划补货）
```

### 2.4 测试隔离：H2 内存库

`erp-reporting-service` / `erp-purchase-service` 的测试通过 `baseMapper.insert()` 真实落库，需要数据库。

**方案**：生产配置走 MySQL，测试配置走 H2（`MODE=MySQL`），并提供 `schema.sql` 自动建表：

```
src/main/resources/application.yml   → MySQL（生产）
src/test/resources/application.yml   → H2 内存库（测试）
src/test/resources/schema.sql        → 建表脚本
```

### 2.5 数据库驱动统一为 MySQL

`docker-compose.yml` 权威配置是 **mysql:8.0**，但多个模块配置为 PostgreSQL。已统一：

| 模块 | 变更 |
|------|------|
| `erp-customer-service` | postgresql → mysql-connector-j |
| `erp-reporting-service` | postgresql → mysql-connector-j |
| `erp-purchase-service` | postgresql → mysql-connector-j + h2(test) |

### 2.6 端口冲突修复

修复前：`8081`×2、`8086`×3、`8087`×3。已重新分配：

| 服务 | 旧端口 | 新端口 |
|------|--------|--------|
| `erp-customer-service` | (无配置) | **8085** |
| `erp-reporting-service` | 8086 | **8092** |
| `erp-purchase-service` | 8087 | **8093** |

### 2.7 逻辑删除配置与实体对齐

`mybatis-plus.global-config.db-config.logic-delete-field: deleted` 会让所有查询自动追加 `deleted = 0` 条件。4 个模块的 entity **没有** `deleted` 字段（表里也没这列），运行时会报 `Unknown column 'deleted'`。

已移除这 4 个模块的逻辑删除配置：
`erp-customer-service`、`erp-inventory-alert-service`、`erp-purchase-service`、`erp-reporting-service`

保留配置的模块（order / platform / product / user）entity 与表结构均有 `deleted` 字段，未改动。

## 六、遗留问题（未在本次修复范围内）
